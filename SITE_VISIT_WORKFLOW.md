# Site Visit Appointment Workflow

This document describes the current Site Visit appointment flow implemented by the application.

## Routes

| Route | Purpose |
|---|---|
| `/appointments/site-visit` | Appointment list, filters, and status overview |
| `/appointments/site-visit/add` | Select protocols and provide request details |
| `/appointments/site-visit/add/schedule` | Select the appointment date and submit the request |
| `/appointments/site-visit/[id]` | View appointment details and perform workflow actions |

## Data and integrations

- Appointment records are read from and written to the Supabase `appointments` table.
- The app uses the table's snake_case fields (for example, `site_visit_no`, `appointment_date`, and `confirmation_notes`) and normalizes them for the UI.
- Site Visit collaboration messages, read receipts, reactions, and system status messages are stored in the appointment row's `messages` JSONB array. Chat reads and updates use the appointment UUID (`id`) and subscribe to Supabase Realtime; the open chat also polls as a fallback.
- Per-user status views are stored in `appointments.viewed_status_by_user`; `PENDING` pings Engineering/IT and `CONFIRMED` pings Sales managers/TSMs/Sales Heads until each user opens the appointment. The column is added by `supabase/add_site_visit_viewed_status_by_user.sql`.
- Appointment version snapshots are stored in `appointments_history`. Apply `supabase/appointments_history.sql` to create the history table and trigger. Existing appointments receive a baseline snapshot; the trigger then records inserts, deletes, and meaningful updates while skipping chat-message and status-view-only updates.
- New appointment IDs are generated by the client. Site Visit numbers are derived from existing Supabase appointment numbers:
  - Production: `PS-YYYY-NNN`
  - Test mode: `TEST-PS-YYYY-NNN`
- Appointment list and detail pages subscribe to Supabase Realtime changes for the `appointments` table. The open detail page also refreshes the current row every five seconds while the browser tab is visible as a fallback if a Realtime event is missed or unavailable.
- Protocol selections are stored in the appointment's `protocols` text array as protocol IDs, not labels. The app resolves those IDs to labels from the protocol catalog. Legacy protocol documents use the Firestore `protocols` collection; Supabase `protocols` rows are also supported. Known legacy IDs have a local label fallback so older appointments can still display readable names if a catalog lookup is unavailable.
- A selected protocol's `pic` list is used to populate available personnel for assignment. Protocol PIC names are matched to `users.ReferenceID`; new assignments store the matched ReferenceID(s) in the appointment's `pic` field.
- When displaying PICs, ReferenceIDs resolve to `users.Firstname` and `users.Lastname`. Older appointment records that already contain PIC names continue to display those values as stored; they are not rewritten.
- Scheduling availability matches both newly stored ReferenceIDs and legacy PIC names.
- Selecting an account loads its contact rows. Comma-separated contact names, designations, email addresses, and phone numbers are split into aligned contact cards. All available contacts are included by default; the requestor can toggle individual contacts or Select All/Clear All. Only selected contact values are saved as comma-separated values in `contact_person`, `designation`, `email`, and `contact_number`. The appointment detail page reconstructs and displays each saved contact with its designation and available contact information.
- Support categories are saved as protocol IDs in `protocols`, resolved to labels, and displayed as blue chips in the appointment detail view.
- The appointment page checks `/api/permissions/check` for the user's `services.siteVisit` permission (or an allowed bypass). The database's Supabase Row Level Security policies must also permit the required reads and writes; UI permission checks alone are not database security.

## Status lifecycle

```text
PENDING ── engineer report submitted ──> CONFIRMED ── Sales manager/TSM or Sales Head acknowledgment ──> COMPLETED
   └──────────────── cancellation ────────────────────────────────────────────────> CANCELLED
```

`IN_PROGRESS` is not a persisted appointment status. "In Progress" is a display/timeline phase while the appointment is still `PENDING`.

## Workflow

### 1. Create and schedule a request

The requestor completes the add-request steps, including client/contact details, agenda, selected protocol IDs, personnel/PPE/permit details, and any attachment. Selecting a client fills one read-only multiline Deployment Address field from the account's `address` value, falling back to `delivery_address`. No separate region, province, city, barangay, street, landmark, or manual address inputs are required. The account's region is retained when available. They select a date and submit the request. Calendar capacity is based on all Engineering users with a non-empty `engiconnect_role`, `Department = Engineering`, `Status = Active`, and a `ReferenceID`; booked PICs reduce the available count.

The app inserts a row into Supabase `appointments` with:

- A generated `id` and `site_visit_no`
- `status = PENDING`
- `pic = UNASSIGNED`
- The request details, selected protocol IDs, appointment date, and optional file URL
- The client's deployment address and region; granular address columns are left blank
- `submitted_by`, `submitted_by_name`, `pending_at`, and `pending_by`
- `created_at` and `updated_at`

The submitter ID is required. After a successful insert, the form is reset, a notification is sent to the submitter's hierarchy, and the user is returned to the appointment list.

### 2. Assign engineering personnel

While status is `PENDING` and no PIC is assigned, a user in Engineering or IT with Site Visit access can select one or more available PICs and confirm the assignment. The picker displays users' first and last names, but saves their `ReferenceID` values. Only users with a non-empty `engiconnect_role`, `Department = Engineering`, and `Status = Active` are eligible; protocol PIC matching still determines which eligible users are available.

- Assignment updates `pic` with one or more comma-separated `users.ReferenceID` values; status remains `PENDING`.
- The update also sets `updated_at` and `last_modified_by`.
- The current assignment action does not set `assigned_at`, `assigned_by`, or `assigned_by_id`. The detail page may still display these fields on older records if they already contain values.

### 3. Submit the engineer's report

When a PIC is assigned and the appointment remains `PENDING`, Engineering or IT users with Site Visit access can enter findings/actions in the confirmation notes and submit the report.

The update sets:

- `status = CONFIRMED`
- `confirmation_notes`
- `confirmed_at` and `confirmed_by`
- `updated_at` and `last_modified_by`

The detail page then shows the report as awaiting Sales Management review. The UI gates this action by department and Site Visit access; it does not verify that the signed-in engineer's name matches the assigned `pic`.

### 4. Acknowledge and finalize

For a `CONFIRMED` appointment, a Sales-department manager, Territory Sales Manager (TSM), or Sales Head with Site Visit access can review the engineer's report and choose **Approve & Finalize**.

The update sets:

- `status = COMPLETED`
- `completed_at` and `completed_by`
- `updated_at` and `last_modified_by`

`COMPLETED` is the final acknowledged state.

### 5. Cancel a pending request

The detail page offers cancellation while the request is `PENDING` to an authorized requestor, Sales user, Engineering/IT staff member, or admin. A reason is required.

The update sets:

- `status = CANCELLED`
- `cancel_reason`
- `cancelled_at`, `cancelled_by`, and `cancelled_by_id`
- `updated_at` and `last_modified_by`

Cancellation is an alternate terminal path; the normal progression cannot be skipped.

## Permission checks

| Action | Required access in the current UI |
|---|---|
| Create a request | A signed-in submitter with a Supabase `ReferenceID` |
| Assign personnel | Site Visit access and Engineering or IT department |
| Submit engineer report | Site Visit access and Engineering or IT department |
| Acknowledge report | Site Visit access and Sales department manager, TSM, or Sales Head |
| Cancel pending request | Site Visit access and requestor, Sales, Engineering/IT, or admin eligibility |

`/api/permissions/check` obtains role permissions from Supabase. It returns a bypass for IT and Procurement, but workflow actions also apply their own department/role checks. A bypass therefore does not automatically make every action available.

## SLA and display behavior

- `PENDING`: 24-hour countdown from `created_at`.
- `CONFIRMED`: 12-hour manager-approval countdown from `confirmed_at`.
- The detail view marks an expired countdown as overdue.
- Status values persisted to Supabase are `PENDING`, `CONFIRMED`, `COMPLETED`, and `CANCELLED`. UI descriptions such as "In Progress," "Awaiting approval," and "Acknowledged" describe phases; they are not additional database statuses.
